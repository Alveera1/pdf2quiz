1. Describe in detail how the ETL process handles heterogeneous sales data received from three branches that use different date formats and currency representations, including the roles of the staging area and data cleaning steps.
   Answer: The ETL process begins with the Extract phase, where data is collected from each branch’s source system. Because each branch uses different date formats (e.g., MM/DD/YYYY, DD-MM-YYYY) and currency representations (e.g., USD, EUR, GBP), the raw data is heterogeneous. The extracted data is then moved to the Staging Area, a temporary holding space where it can be validated and prepared for transformation. In the Transform phase, data cleansing operations are applied: dates are parsed and converted into a uniform format such as ISO 8601, currencies are converted to a single base currency using current exchange rates, and any invalid or missing values are standardized or flagged for review. Additional transformations may include joining related records, filtering out irrelevant rows, and standardizing business terminology so that all records align. Once the data is clean, consistent, and validated in the staging area, the Load phase writes the prepared data into the data warehouse’s central repository. This sequence ensures that the warehouse contains integrated, historical data that can be reliably used for reporting, analysis, and business intelligence.

2. Contrast the architectural and operational differences between OLTP systems and Data Warehouse/OLAP systems, focusing on data volatility, normalization, query complexity, and typical user roles, and explain why these differences justify distinct system designs.
   Answer: OLTP systems are optimized for daily transaction processing; they handle current data that is frequently inserted, updated, and deleted. Their tables are highly normalized to reduce redundancy and support efficient transactional writes. Users of OLTP systems are generally clerks and application programs that require fast, accurate data entry and retrieval for day‑to‑day operations. Queries in OLTP are short, simple, and frequent, designed to support the immediate needs of the business. In contrast, Data Warehouse/OLAP systems store both current and historical data, which is largely read‑only and non‑volatile. The data is denormalized or organized in dimensional models (fact and dimension tables) to facilitate complex analytical queries that aggregate and slice large volumes of historical information. Users are analysts, managers, and data scientists who perform trend analysis and decision support, requiring more complex, longer‑running queries such as roll‑ups, drill‑downs, and pivot operations. Because OLTP emphasizes transaction integrity and speed, while OLAP emphasizes analytical flexibility and performance on large datasets, they require distinct architectures: OLTP uses normalized schemas and frequent updates, whereas OLAP uses dimensional schemas and read‑heavy workloads.

3. Explain the trade‑offs between adopting a star schema and a snowflake schema in a dimensional model, covering impacts on query performance, data redundancy, join complexity, and maintenance, and give scenarios where each design would be preferable.
   Answer: A star schema centralizes a single fact table that connects directly to several dimension tables. This design is simple and supports fast analytical queries because it requires a minimal number of joins; each dimension is stored in a denormalized form, which increases redundancy but simplifies query logic. It is ideal when query performance is paramount and the data model is relatively stable, such as in a sales reporting system where quick access to aggregated metrics is essential. A snowflake schema extends the star by normalizing dimension tables into related sub‑tables, reducing redundancy and storage overhead. However, the deeper normalization introduces additional joins, which can slow query performance, especially on large data volumes. Maintenance becomes more complex because changes must propagate through multiple related tables. The snowflake is preferable when data redundancy is a significant concern, or when dimensions have many attributes that vary rarely and can be logically split, such as a complex product hierarchy. Therefore, the choice hinges on a trade‑off between minimizing storage and simplifying queries (star) versus reducing redundancy and simplifying data updates (snowflake).
